# ADR-0024 精錬報酬を投入者への精錬完了ベースにする

## ステータス

受け入れ

## 背景

`item_smelted` の報酬は `FurnaceExtractEvent` を起点にしていた。
取り出したプレイヤーに、取り出した個数分を払う形である。
投入者の追跡は [ADR-0017](./0017-operator-tracking-common.md) の `op:` キーが担い、「直近に人が投入したか」という真偽に近い情報だけを TTL 60 秒で持っていた。

この形には 4 つの問題がある。

第一に、TTL が精錬時間に対して短い。
かまどの精錬は 1 個 10 秒、溶鉱炉と燻製器は 1 個 5 秒である。
64 個を手動投入して焼き上がりを待つと 5 分から 11 分かかる。
その間に `op:` への追記が起きなければ TTL が切れ、正当な手動投入が `auto_fed_processing` で 0 になる。
ADR-0017 は「TTL 60 秒は手動投入から取り出しまでの現実的な時間を余裕を持って包含する」と判断したが、その見積りは 1 サイクル分の時間しか勘定に入れていない。

第二に、追跡を入力スロットに限定できていない。
ADR-0017 は燃料スロットを追跡対象外と決めた。
石炭のホッパー供給という正当な運用を巻き込まないためである。
しかし `InventoryClickEvent` からは「容器側のスロットか」しか分からず、`InventoryMoveItemEvent` は宛先スロットを教えない。
イベント単体からは入力と燃料を切り分けられないので、燃料をホッパー供給する構成では、手動投入した材料の報酬まで 0 になる。

第三に、報酬の帰属先が取り出した人になる。
ADR-0017 は協力プレイを守るために extractor と operator の一致を求めない決定をした。
その判断自体は妥当だが、結果として材料を用意して焼いた側ではなく、最後に蓋を開けた側に報酬が出る。

第四に、手動投入・ホッパー搬出という半自動構成では `FurnaceExtractEvent` が発火しない。
投入という人の関与があるのに報酬が 0 になる。

4 つはいずれも同じ根に生えている。
「誰が何個投入したか」を持たず、「直近に誰かが触った」という真偽値へ潰していることである。
個数の帰属を持てば、まとめて解ける。

## 決定

精錬の報酬を「投入者への精錬完了ベース」に変える。

### 精錬元帳を Block PDC に持つ

かまど（Furnace / BlastFurnace / Smoker）の PDC に、投入順の元帳を持つ。

- key：`jobs:smelt_ledger`
- 型：`BYTE_ARRAY`
- 内容：バージョン、入力アイテムの種別、`(所有者 UUID または null, 個数)` の FIFO

所有者 null は hopper / dispenser / dropper 由来の自動投入を表す。
自動投入分も順序を保って記録する。
省くと「A が 8 個入れた後にホッパーが 56 個入れた」ケースで消費位置がずれる。

エントリ数の上限は 8 とし、超過時は最古の 2 件を合算する。
合算先の所有者は古い側に寄せる。

### 元帳は入力スロットの実個数へ同期させる

イベントは「直前に触ったのは誰か」のヒントとしてのみ使い、スロット位置は推測しない。

投入系イベント（`InventoryClickEvent` / `InventoryDragEvent` / `InventoryMoveItemEvent`）を受けたら、そのブロックの照合を 1 tick 後に予約する。
イベント時点ではまだアイテムが動いていないので、同 tick で入力スロットを読んでも古い値になる。
照合では `FurnaceInventory#getSmelting()` の実個数と元帳合計を突き合わせ、増分を直前の接触者へ帰属させ、減分は新しいエントリから削る。

この形にすると、背景の第二の問題が構造的に消える。
燃料スロットへの投入では入力スロットが動かないので元帳が変わらない。
ドラッグ投入や、入れたものを取り出し直す操作も同じ経路で吸収される。

入力スロットのアイテム種別が元帳の記録と異なる場合は元帳を破棄する。
別の材料に入れ替えたとき、前の材料の帰属を引き継がせない。

### 報酬は FurnaceSmeltEvent で確定する

1 個焼き上がるごとに元帳の先頭から 1 個を消費し、その所有者へ払う。

投入時には払わない。
入れてすぐ取り出すループで、燃料も時間も消費せずに稼げてしまう。

所有者が null なら支払わず消費だけを行う。
`auto_fed_processing` のかまど分はこの一点に吸収され、同対策の対象は BrewingStand だけになる。

所有者がオフラインなら支払わず消費だけを行う。
専業の取得、bypass 権限の解決、`VarietyRingBuffer`、ActionBar 通知はいずれも online な `Player` を前提にしており、[ADR-0021](./0021-async-reward-pipeline.md) の実行モデルも `Player` の強参照を持つ。
「投入して放置ログアウト」は稼げない仕様とする。

### amount は集約して 1 件にする

`(所有者, ブロック, アイテム)` 単位で一定 tick 分まとめ、`amount` に畳んで 1 件として dispatch する。

1 個ごとに 1 件にすると、64 個スタックで 64 件になる。
イベント件数だけでなく `variety_penalty` の意味論も変わる（従来は取り出し 1 回で 1 件）。
集約は従来の粒度を保つための決定でもある。

### 取り出し起点の報酬は撤去する

`FurnaceExtractEvent` からの `item_smelted` dispatch は削除する。
残すと二重支払いになる。

`on: item_smelted` の YAML 定義と派生キー `smelt:<item>` は変えない。
運用者の設定は無変更のまま、意味が「取り出した個数」から「精錬が完了した個数」に変わる。

## 結果

- 手動投入して焼き上がりを待つという最も普通の遊び方が、TTL 切れで 0 にならない。
- 燃料のホッパー供給と材料の手動投入が混在する構成で、材料分が正しく払われる。
- 手動投入・ホッパー搬出の半自動構成でも、投入した個数分が払われる。
- 報酬が材料を用意した側に出る。取り出しは誰がやってもよい。
- 元帳がチャンクと共に保存されるので、再起動を跨いだ精錬でも帰属が残る。
- `auto_fed_processing` はかまど分を失い、BrewingStand 専用の対策になる。設定名と挙動は BrewingStand について変わらない。
- 投入者がオフラインになった分の報酬は失われる。
- 元帳はかまどブロックの寿命に縛られる。ブロックを壊せば中身のドロップと共に消える。

## 選択しなかった代替案

`operator_ttl_sec` を延長する案は、TTL 切れだけを緩和して他の 3 問題を残す。
延長した TTL は `kvs.memory.max_entries` の上限に当たりやすくなり、長時間の精錬が eviction で消える経路も増える。

元帳を KVS に持つ案（[ADR-0015](./0015-kvs-abstraction.md) の方針に沿う形）は採らない。
ADR-0015 が KVS を選んだ理由は、`recently_placed_break` が全ブロック対象で書き込み頻度が高く、TTL による自動失効が要件だったことにある。
精錬元帳は逆の性質を持つ。
TTL を持たない長寿命データで、書き込み頻度はかまどへの投入と精錬完了に限られ、消えたときの実害は「報酬が消える」という向きに出る。
in-memory KVS では再起動と `max_entries` の eviction の両方で失われる。
データの寿命をかまどブロックの寿命に一致させられるストレージは PDC である。

投入時に個数分を払う案は、入れて即取り出すループで無限に稼げる。

1 個ごとに 1 件を dispatch する案は、`variety_penalty` の窓の意味論を従来から変えてしまう。

オフラインの投入者にも払う案は、専業・日次キャップ・単調性ペナルティをオフラインで解決する経路を新設することになる。
ADR-0021 の実行モデルにも `Player` 前提が埋まっており、影響範囲が精錬の枠を超える。

`FurnaceExtractEvent` を残したまま元帳で帰属だけ差し替える案は、ホッパー搬出の構成を救えない。
取り出し個数と元帳の対応付けも、部分取り出しや複数回取り出しで煩雑になる。
