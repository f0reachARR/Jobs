# ADR-0023 recently_placed の判定を再設置にも広げる

## ステータス

受け入れ

## 背景

[ADR-0016](./0016-recently-placed-break.md) は「直近に置かれた block の破壊は placer を問わず 0」を決めた。
判定は `block_broken` にだけ効き、KVS の `place:<world>:<x>:<y>:<z>` が残っていれば 0 にする。

しかしこの判定は破壊側にしか効かない。
`block_placed` に報酬を付けたジョブでは、置く → 壊す → また置く のループで設置報酬を無限に稼げる。
破壊側は `recently_placed_break` で 0 になるが、設置側は素通りするため、ループは成立したままである。

作物ではこの穴がさらに開いている。
ADR-0016 は「作物は成長時間の関係で 1 時間窓に自然に該当してしまう」として `Ageable` を追跡対象から外し、`PlacementRecorder` が `Ageable` を記録しない実装になっていた。
記録が無いので、種を植える → 壊す → また植える のループは位置の追跡自体が効かない。

## 決定

`place:` が残っている位置への **設置** も報酬 0 にする。
判定は新しい check `recently_placed_replace` として実装し、ON/OFF と `window_sec` は既存の `anti_automation.recently_placed_break` を共有する。

```yaml
anti_automation:
  recently_placed_break:
    window_sec: 3600    # 破壊側と設置側の両方に効く
```

設置側は `Ageable` を含む全ての block を対象にする。
作物を除外すると、上に書いた「種を植える → 壊す → また植える」がそのまま抜け道として残るためである。
これに伴い `PlacementRecorder` の `Ageable` スキップを外し、作物の設置も `place:` に記録する。

ADR-0016 の「作物は追跡対象外」は、以後 **破壊側の判定に限った除外** として読む。
除外の理由は「正当な収穫を巻き込む」ことであり、これは破壊側でのみ生じる。
`RecentlyPlacedBreakCheck` は記録の有無にかかわらず `Ageable` を素通しし続けるので、ADR-0016 が守ろうとした収穫は影響を受けない。

設定キーを増やさず既存 section を共有するのは、両者が同じ「位置の追跡窓」という 1 つの概念だからである。
別々の窓を持てる利点より、有効化の口が 2 つに割れて設定を誤る不利益が上回ると判断した。

## 結果

- 置く → 壊す → また置く のループは、破壊側と設置側の両方で 0 になる。
- 作物の設置も `place:` に記録されるため、KVS のエントリ数は農業系の稼働分だけ増える。
  `InMemoryKVStore` は `kvs.memory.max_entries`（既定 500,000）を超えるとランダム evict する。
  既定値は 1 時間窓に対して十分な余裕があるが、evict が起きると追跡窓に穴が空くため、`/jobs admin kvs stats` で総数を見られるようにしてある。
- 位置ベースの判定なので、壊して別のブロックを置き直す張り替えも窓の間は 0 になる。
  ADR-0016 が破壊側で既に受け入れた性質と対称であり、置き直しを許すとブロックの種別を KVS に持つ必要が生じるうえ、種別を変えるだけの抜け道も開く。
- `BlockPlaceListener` は dispatch を済ませてから `PlacementRecorder` を呼ぶ順序に変わる。
  設置側の判定は「この設置より前に置かれた記録」を読む必要があり、先に記録すると自分の書いたマーカーを読んで初回の設置まで 0 になるためである。
  段階 3 は `Stage.Affinity.MAIN` で prologue として同期実行される（[ADR-0021](./0021-async-reward-pipeline.md)）ので、dispatch から戻った時点で判定は済んでいる。
- 既に `recently_placed_break` を有効にしているサーバーでは、`block_placed` 報酬の挙動が変わる。

## 選択しなかった代替案

独立した設定キー（`repeat_placement` など）を別 window で持たせる案は、設定の柔軟性は上がるが有効化の口が 2 つに割れる。
「recently_placed_break を入れたのに設置ループが止まらない」という今回と同じ取り違えを、名前を変えて再生産する。

設置側の判定を作物に限定する案は、今回の報告に直接は答えられる。
しかし石ブロックなどでの同じループが残り、位置追跡という仕組みを持ちながら一部の block でだけ効かせない理由が説明できない。

`BlockBreakEvent` で `place:` を消して「壊したら記録も消える」形にする案は、置く → 壊す → また置く のループをむしろ通してしまう。
記録を TTL まで残すことが、このループを検出する条件そのものである。
