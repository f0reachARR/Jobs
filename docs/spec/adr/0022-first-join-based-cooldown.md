# ADR-0022 変更クールダウンを初参加からの経過時間で分岐する

## ステータス

受け入れ

## 背景

専業変更のクールダウンは `config.specialty_mode.change_policy` で決まる。
これまで `within` に書けた条件は `event_hours` だけで、時間帯によってクールダウンを変えることしかできなかった。

サーバーに来たばかりのプレイヤーは、どの職業が自分に合うかを知らないまま最初の 1 つを選ぶ。
そこに `5d` のクールダウンをそのまま適用すると、合わない職業を選んだ新規プレイヤーが 5 日間動けなくなる。
一方で、既存プレイヤーの職業を頻繁に変えられる状態にはしたくない。
この 2 つを両立するには「サーバー初参加からの経過時間」を条件に取れる必要がある。

初参加時刻をどこから取るかで、2 つの選択肢がある。

Bukkit の playerdata は `OfflinePlayer#getFirstPlayed` で初参加時刻を返す。
サーバー自身が既に持っている情報なので、スキーマ変更も移行も要らず、既存プレイヤーにも最初から正しい値が入っている。

自前で `first_join_at` を持つ案もある。
DB を共有する複数サーバーで一貫し、playerdata の削除に影響されないが、テーブル追加と既存プレイヤーのバックフィルが必要になる。

## 決定

`within` に `first_join_within: <duration>` を追加する。
`now < 初参加時刻 + 値` のときマッチする。

初参加時刻の取得元は Bukkit の `getFirstPlayed` とする。
取得経路は `FirstJoinProvider` インタフェースの背後に隠し、実装 `BukkitFirstJoinProvider` を差し込む。
インタフェースを挟むのは、後から自前 DB 方式へ移る余地を残すためと、`CooldownPolicy` の単体テストを Bukkit 非依存に保つためである。

### 意味論

`within` に複数のキーを書いた場合は、すべて満たしたときだけマッチする（AND）。
キーを 1 つも持たない `within` はどのポリシーにもマッチしない（従来どおり）。

「N 時間経過後」に相当する否定条件は導入しない。
`change_policy` は first match wins（[ADR-0004](./0004-first-match-wins.md)）なので、後続のポリシーか `default` が受ければ足りる。

初参加時刻が取得できないプレイヤーでは、`first_join_within` を持つポリシーはマッチしない。
不明を「新規」とみなすと、判定できないプレイヤー全員に短いクールダウンを配ってしまう。
より長い `default` 側へ落とすほうが安全側に倒れる。

例外はオンライン経路で `getFirstPlayed` が 0 を返した場合で、このときだけ「今まさに初参加した」とみなす。
今ログインしているプレイヤーの playerdata がまだ書かれていない状況であり、これは新規プレイヤーそのものだからである。

### 評価タイミング

判定は評価のたびに policy を引き直す。
`player_job` は `cooldown_base_at` だけを保持し、解決済みのクールダウンは保存しない（[05-persistence.md](../05-persistence.md)）。

### 参照コスト

`getFirstPlayed` はオフラインの `OfflinePlayer` に対して playerdata を読むため、ディスク I/O が走る。
`BukkitFirstJoinProvider` はログイン時に値をキャッシュへ温め、ログアウトで捨てる。
オンラインのプレイヤーに対する判定は、この cooldown 判定の経路でディスクに触らない。

## 結果

- 新規プレイヤーだけクールダウンを短くする運用ができる。既存プレイヤーの設定は変えなくてよい。
- `within` が AND になったことで、`event_hours` と組み合わせた「イベント時間帯かつ初参加 30 日以内」のような条件も書ける。
- 初参加からの経過がしきい値を跨いだ瞬間、同じ `cooldown_base_at` に対する「次回変更可能時刻」が後退する。初参加 71 時間目に `1h` のポリシーで変更したプレイヤーは、72 時間を跨いだ時点で `base + 5d` を見ることになる。`event_hours` にも元からある挙動だが、初参加条件は全員が必ず 1 回跨ぐため、遭遇頻度は上がる。
- 初参加時刻は playerdata に依存する。複数バックエンド構成では各サーバーごとの値になり、playerdata を消すと初参加時刻もリセットされる。
- `/jobs admin inspect` に初参加時刻と適用中のクールダウンを出す。プレイヤー間でクールダウンが違う理由を、運用側が問い合わせのたびに追えるようにするため。
- playerdata を読む経路はオフライン相手の `/jobs admin inspect` だけになる。公開 API の `PlayerJobService#nextChangeAvailableAt` は `cooldown_base_at` のキャッシュ依存でオフラインでは `empty` を返すため（[06-public-api.md](../06-public-api.md)）、この経路には乗らない。

## 選択しなかった代替案

- **自前 DB に `first_join_at` を持つ案**：DB を共有する複数サーバーで一貫し、playerdata の削除にも影響されない。ただしテーブル追加と既存プレイヤーのバックフィルが必要で、バックフィルの入力は結局 `getFirstPlayed` になる。単一サーバー運用では利点が出ないので採らなかった。`FirstJoinProvider` を差し替えれば後から移行できる。
- **`first_join_hours: [min, max]` と範囲で書く案**：`event_hours` と対称になり「初参加 24〜72 時間の間だけ」のような帯も書ける。ただし単位が時間固定になり `cooldown` の duration 記法と揃わない。帯が要る場面は、ポリシーを並べる順序で表現できる。
- **変更時点のクールダウンを確定保存する案**：しきい値を跨いでも次回変更可能時刻が動かなくなり、プレイヤーから見た挙動が安定する。ただし `player_job` にカラムを足すことになり、`event_hours` を含む既存の挙動まで変わる。base だけを保持して毎回再評価する判断（[05-persistence.md](../05-persistence.md)）を覆すほどの理由がない。
